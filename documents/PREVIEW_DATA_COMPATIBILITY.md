# First Signal preview: maintained and disposable Entities

Application/data compatibility status, 2026-10-20. The intended preview workflow is one ongoing Entity whose identity and history survive application updates, alongside disposable Entities used for creation and maintenance checks. Application profile isolation and the bounded [Windows cold-recovery slice](PREVIEW_COLD_RECOVERY.md) are implemented in development source. Recovery was published at `4558fe68d9812998eb53a94ba157970af552f923` and is included in the combined dev candidate. Its prior [component validation](../output/playwright/cold-profile-validation.md) passed 104 distinct Rust tests—101 core and three actual SurrealKV fresh-process recovery tests—and seven separately counted CLI smoke checks, with three ignored child fixtures and no unresolved blocking review findings. The archived record's publication-pending wording describes its earlier checkpoint; [combined validation](../docs/PREVIEW_COMBINED_VALIDATION.md) records fresh candidate checks separately. Recovery does not change release workflows, channels, installer routing, or actual user Entities.

## Data compatibility boundary

The earlier application comparison with signed stable source `e3ad511` retained the persistence engine/schema, supported `AppConfig` migration transformations and schema version 27, and stable data-root defaults. The current combined source additionally uses the distinct preview packaging identities recorded in [release alignment](PREVIEW_RELEASE_ALIGNMENT.md); stable base Tauri identifiers remain unchanged. Preview source adds an explicit immutable profile context, active-profile startup preflight, and refusal of unsupported schemas before config loading or replacement. Active configs are also bound to their selected UUID directory before migration or use. These are component boundaries; exact installed acceptance remains open.

Identity directories remain `identities/<UUID>`, and Hive owns the shared `memory.db`. Preview user Documents, temporary files, archives, backups, logs and WebView data now derive from the validated preview root; credential selection has its own profile namespace. Presentation remains a separate `presence.json` sidecar. An existing Entity without one gets non-writing defaults, while invalid saved presentation is reported rather than silently reset.

The new global `creation_attempts` field has a deserialization default. A populated prior registry can load without it; future keyed creation adds receipts while retaining the prior registered IDs, directories, and settings. An existing born Entity is opened without re-running the new-Entity quickstart. Imported visual briefs remain presentation metadata, not a rewrite of existing identity documents or permissions.

This is forward compatibility with the inspected stable data format. It is not proof of an installed-version upgrade or arbitrary downgrade compatibility. An older binary can deserialize unknown registry fields and later omit them when saving, so rolling back across the creation-receipt addition is not a supported way to preserve pending creation recovery. A pre-update data snapshot and restoration procedure require separate release acceptance.

## Operational constraints for the first usable preview

- Keep the ongoing Entity's UUID and Hive data root unchanged. Use one Hive owner for that root; do not run different app versions concurrently against it.
- Use separate Entity IDs for disposable work, not just another session in the ongoing Entity. Recall can span sessions within one Entity, and normal reopen selects its latest session. A whole Hive data-root snapshot is necessary: identity directories alone omit the shared `memory.db` SurrealKV directory. The [implemented cold-recovery source](PREVIEW_COLD_RECOVERY.md) copies the entire retained root, including Documents, archives and WebView storage, while preserving profile/Entity UUIDs and creation receipts. It requires cold ownership, probes existing same-user/device credentials and publishes only to a fresh destination. The completed 101 core and three actual SurrealKV fresh-process tests use synthetic data/fake credentials; seven CLI smoke checks cover help/parser/missing-input behavior without credential access. Real OS credential/GUI/installed acceptance remains separate. No actual user data was read or copied.
- Preview Documents use `R/Documents/<UUID>`, so equal names do not share those directories. Stable name-based Documents behavior remains unchanged; this work does not move existing Documents. A copied stable or experimental config is not implicitly migrated into a preview root.
- Preview adopts a daemon only after checking channel, profile UUID, canonical root and expected live process instances. Close/cleanup uses verified instances and owned handles, not a descriptor PID. These identities do not prove executable revisions; exact candidate acceptance must still verify the intended binary hashes and supported restart lifecycle.
- A changed browser origin can lose browser-local drafts/session hints. The authoritative Entity registry, presentation, and committed conversation history are server-side; browser storage is not a replacement for those files. A cleared creation key cannot be reconstructed safely from an Entity name.
- Existing Entity deletion removes its registry entry and identity directory; it does not purge that Entity's records from the shared database. The disposable tests do not claim complete history erasure. Preview startup rejects inherited `ABIGAIL_CI_MODE`/`ABIGAIL_DAEMON_INTEGRATION` test modes; the existing stable test path can deliberately substitute ephemeral storage and is not durability acceptance.
- `migrate_legacy_layout` exists in `crates/abigail-persistence/src/migration.rs`, but no active caller was found in the inspected source. Do not claim automatic migration of arbitrary old SQLite layouts. This integration does not change that legacy path.
- Stopping a profile PUT can leave an uncertain accepted server write. Its current contract has no revision precondition; avoid simultaneous profile editing from multiple clients during this preview.
- The inherited server cancellation slot in `crates/entity-daemon/src/routes.rs` is not turn-scoped. A delayed Stop for an earlier turn or that turn's cleanup can affect a newer turn after rapid resend. The UI tests do not validate server ownership of cancellation; a separate bounded fix needs deterministic overlapping-turn handler tests.
- A retained creation-journal URL that differs from the verified preview endpoint fails explicitly. The exact key remains stored; automatic same-profile endpoint rebinding is not implemented. Never silently retarget an uncertain attempt or replace its key.

## Minimum remaining acceptance before recommending a signed preview update

The [preview profile contract](PREVIEW_PROFILE_CONTRACT.md) now describes implemented application guards for startup, paths, credentials and connection ownership. A custom data-root variable alone still does not establish that contract. Synthetic component validation must be distinguished from real OS credential integration and the final installed candidate.

The [release alignment](PREVIEW_RELEASE_ALIGNMENT.md) maps application work to the exact ten stages required by release scaffolding `6b246d3`. Source-level schema/preflight refusal is narrower than its installed `newer-schema-refusal` stage. Fresh creation acceptance must use a separate fixture from the continuing-profile upgrade test.

1. Verify exact UUID/history/decryption recovery in the installed environment using the published recovery source. Its prior [component record](../output/playwright/cold-profile-validation.md) passed 104 distinct Rust tests and seven separate CLI smoke checks; current combined reruns remain separate. Recovery uses cold leases, a whole-root inventory, declared-path rebasing, existing-credential verification and no-overwrite publication; runtime descriptors are excluded. The offline utility is separate from the four packaged application binaries, so installed recovery requires a reviewed tooling plan. Per-Entity restore still creates a new UUID and is unchanged.
2. On a disposable maintained-profile fixture, verify the actual signed candidate update/restart preserves the same UUID, identity/certificate files, presentation, and exact committed transcript, while creating/removing a distinct disposable Entity leaves the maintained one intact. Verify the expected native/daemon revisions and unchanged data root. The release-engineering owner controls this candidate and installer check.
3. Exercise normal preview bootstrap and OS credentials under a reviewed isolated plan. Fake credential adapters now exercise namespace selection, root-bound caching, fallback and ciphertext separation without OS access. They do not validate Windows Credential Manager/DPAPI integration. [STARTUP_TEST_ISOLATION_PLAN.md](STARTUP_TEST_ISOLATION_PLAN.md) records the earlier access inventory and test-only approach.

The unresolved viewport approval limits narrow-screen evidence; no current mobile-layout pass is claimed. It does not establish a failure of the desktop layout. Actual generated video/audio, beta Genesis reconciliation, complete skill lifecycle work, and durable cross-process bus replacement are not prerequisites for evaluating this existing procedural desktop interaction slice.
