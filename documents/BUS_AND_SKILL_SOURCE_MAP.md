## Transport and the Iggy/SurrealDB claim

The current active Entity daemon uses **an in-process message bus plus SurrealDB persistence**. Iggy and SurrealDB are not competing replacements in this architecture.

- `crates/entity-daemon/src/main.rs:244` explicitly ignores `--iggy-connection` and constructs `MemoryBroker::default()` at line 253. This is stronger evidence than older comments describing a phased Iggy rollout.
- `crates/abigail-streaming/src/broker.rs:18` defines `StreamBroker`: publish, poll, subscribe, topic/group creation, acknowledgement, and shutdown. `memory_broker.rs:98` broadcasts messages with Tokio; `:135` subscribes live receivers. It is not a durable event log and does not provide restart replay. `iggy_broker.rs:1` contains a real native-Iggy adapter, but the active daemon does not select it.
- `crates/abigail-streaming/src/bus.rs:19` defines stream `entity`. Canonical topic names at `:53` include `mentor.input`, `id.reaction`, `id.signal`, `ego.deliberation`, `ego.action`, `conscience.check`, `superego.evaluation`, `job.events`, `skill.executed`, `memory.archive`, `hive.outbound`, and `governance.inbound`.
- The canonical `Envelope` (`bus.rs:110`) contains topic, entity ID, timestamp, optional soul reference, correlation ID, and JSON payload. `:145` duplicates routing/correlation fields in `StreamMessage` headers. Not every producer uses this schema: mentor input uses `MentorChatEnvelope` (`crates/abigail-router/src/monitor/mentor_chat.rs:28`), while Forge has dedicated request/response schemas (`crates/soul-forge/src/lib.rs:442`, `:465`). Consumers must respect those actual schemas.
- SurrealDB is the persistence layer. Runtime startup configures Hive persistence transport (`crates/entity-daemon/src/main.rs:132`); `PersistenceHandle::open` selects that configured remote transport (`crates/abigail-persistence/src/client.rs:123`). The embedded owner is Hive (`crates/hive-daemon/src/persistence.rs:1`); embedded storage opens SurrealKV and syncs every commit (`crates/abigail-persistence/src/client.rs:474`). This does not make SurrealDB the bus broker.

Thus an assertion that Abigail currently runs Iggy as its active bus is contradicted by startup source. An assertion that it uses SurrealDB for persistence is supported. No claim about Iris's own implementation was verified because its library was outside scope.

The existing cross-process control path is Hive HTTP -> Entity polling -> the Entity-local bus (`crates/entity-daemon/src/hive_client.rs:203`, `main.rs:953`, `pipeline/governance.rs:21`). A new Hive-local `MemoryBroker` would not reach the Entity's subscribers. Reuse that HTTP/poll boundary for desired/applied skill revisions rather than assuming a shared in-memory broker.

## Runtime layers actually wired

| Layer | Implementation and limits |
| --- | --- |
| Entry/turn ownership | HTTP and SSE chat call `begin_turn` (`crates/entity-daemon/src/routes.rs:299`, `:388`). It publishes `MentorInput` and records a correlation ID (`pipeline/mod.rs:135`). Cancellation, streaming senders, and result oneshots remain in an in-process `TurnRegistry` (`:39`, `:52`); bus messages alone cannot resume a turn after process restart. |
| Id stage | `pipeline/id_stage.rs:75` builds the prompt from identity documents, instruction registry, runtime context, and constitutional enrichment. An optional local Id consult runs only with local HTTP and Ego availability (`:124`), uses `force_id_only`, has an eight-second limit, and records skipped/error/timeout outcomes rather than inventing a signal (`:169`). It publishes `IdReaction` (`:155`). |
| Ego stage | `pipeline/ego_stage.rs:40` claims the live turn, builds context from memory and registered tools (`:85`), then executes the actual provider/tool loop. Streaming uses the relay (`:104`). Router selection/fallback is centralized in `crates/abigail-router/src/router.rs:595`; forced Id requests suppress Ego fallback. It publishes trace/action messages and returns the outcome (`ego_stage.rs:175`, `:279`, `:293`). |
| Superego | The synchronous pattern evaluator gates final replies (`pipeline/ego_stage.rs:194`); streaming has an incremental relay with a 64-byte withheld tail (`pipeline/stream_gate.rs:24`, `:36`). A separate subscriber observes committed chat, jobs, and skill events (`pipeline/superego_stage.rs:46`) and optionally asks the local Id provider for a constitution-based judgment with a 20-second budget (`:120`). That latter judgment is asynchronous observation, not a pre-execution approval. |
| Monitors/journal/governance | Additional keyword-based Id/Superego monitors consume enriched mentor envelopes (`crates/abigail-id/src/monitor.rs:60`; `crates/abigail-superego/src/monitor.rs:100`). Ego persists a successful assistant turn before acknowledgement (`pipeline/ego_stage.rs:260`); journal queues Hive outbox records and lifecycle events (`pipeline/journal.rs:54`). Governance refresh hot-swaps providers and records assignments (`pipeline/governance.rs:49`). |

These are named software stages and signals, not evidence of sentience or a general guarantee of ethical reasoning. Existing pattern checks, asynchronous observations, and actual permission/confirmation checks should remain distinct in UI and documentation.

## Extension contracts to reuse

`Skill` defines manifest, lifecycle, health, tools, execution, capability lookup, and triggers (`crates/abigail-skills/src/skill.rs:206`). `ToolDescriptor` carries parameter/return schemas, required permissions, and confirmation flags (`:73`); `SkillManifest` adds version, platform, capabilities, permissions, and declared secrets (`manifest.rs:59`). Registry capability discovery is at `registry.rs:126`. Chat derives qualified `skill_id::tool_name` definitions from the real registry (`crates/entity-chat/src/lib.rs:631`).

`SkillExecutor` is the existing invocation boundary: policy, explicit confirmation when required, sandbox permission checks, concurrency limit, timeout, and execution audit (`crates/abigail-skills/src/executor.rs:188`); audit publishes through `skill.executed` (`:65`). Reuse it rather than directly calling implementations from a new UI. HTTP MCP uses `McpSkillRuntime` and descriptor conversion (`protocol/mcp.rs:290`, `:318`). WASM execution is explicitly `WasmRuntimeStub` (`runtime/wasm.rs:18`), not an installed runtime. The older `CapabilityEnvelope` is described as reserved/not applied by the executor (`crates/abigail-core/src/capability_envelope.rs:1`), so it should not be presented as the active enforcement mechanism.

The provisioned skill-topic workers are not an alternative executor: `crates/abigail-skills/src/lib.rs:255-262` responds with `status: "received"` and metadata, without invoking `SkillExecutor` or loading generated code. `topology.rs:173-179` has the same receipt-only behavior. A topology receipt or Forge's `hot_reload_triggered` response must not be displayed as successful runtime tool activation.

The existing HTTP status endpoints are `GET /v1/skills` and `/v1/skills/acks` (`crates/entity-daemon/src/routes.rs:559`, `:603`). `SkillApplyAcknowledgement` at `crates/entity-core/src/lib.rs:357` carries skill ID, status, and timestamp, without an operation ID, revision, artifact digest, or failure detail. The explicit execution route at `entity-daemon/src/routes.rs:616` calls `execute_with_confirmation`; retain that executor boundary.

Two update behaviors need deliberate treatment in a lifecycle design. Forge's existing-ID registry upsert rewrites the old content to trigger the watcher without updating its keywords/topics (`crates/soul-forge/src/lib.rs:998-1002`). The Entity's removed-JSON branch attempts to read the removed file (`crates/entity-daemon/src/main.rs:733`); retain installed IDs/revisions explicitly instead of inferring them from deletion events.

## Recommended next bounded slice

Build one **local dynamic-API package review and activation flow** using existing Hive ownership, dynamic configuration parser, registry/executor, watcher, and entity bus. Start with one synthetic package and no new provider or credentials. Separate states visibly: imported, validated, approved, artifact written, runtime registered, and tested. Persist the package digest and prior accepted JSON before replacement; display actual runtime acknowledgement, not merely an assignment refresh. Reapplying a retained validated prior package can become the narrowly scoped rollback operation.

Use existing Forge request/response correlation where applicable and existing governance/event topics for lifecycle reporting; define typed stage payloads rather than introduce another transport. A test fixture should prove invalid input leaves the current skill intact, approval targets the reviewed digest, activation produces the expected tool descriptor, a synthetic invocation passes through `SkillExecutor`, failed replacement preserves the last working version, and rollback restores it. Generated Rust/script compilation, WASM, autonomous installation, and cross-process durable bus migration should remain separate follow-up work.

Parent-owned overlap with First Signal is limited to Hive `main.rs`/`routes.rs`, `hive-core/src/lib.rs`, `entity-daemon/src/hive_client.rs`, and Hive UI `App.tsx`, `PresenceHome.tsx`, and `lib/daemonClient.ts`. Entity UI shell/ChatPanel would overlap if runtime skill status is exposed there. Keep creation transport/journals, presence profiles, the creation-attempt ledger, and dependency files outside individual skill workers' scope.

Persist an operation ID, exact revision/digest, approval of those bytes, and desired/applied state. Validate and initialize before replacing the runtime entry; preserve the prior accepted artifact. Report `registered` only after actual registry success, and keep that distinct from `execution tested`. Duplicate activation must be idempotent, and a dropped notification or restart must reconcile from persisted state. Rollback targets a specific prior revision and awaits its real acknowledgement. Treat Markdown as reviewed documentation initially; live prompt refresh needs its own tested mechanism.

Suggested tests include invalid-import preservation, approval-digest mismatch, failed registration retaining the previous implementation, exact revision acknowledgement, duplicate activation, restart reconciliation, rollback descriptor restoration, and timeout remaining pending until resolved. Existing source test references include `entity-daemon/tests/integration_skills.rs:67`, `:96`, `:336`, `:442`, `abigail-skills/src/dynamic.rs:894`, and `soul-forge/src/lib.rs:1257`. Use an injected synthetic transport or Skill through the real executor for isolated execution evidence; do not weaken dynamic URL checks for a fixture or present it as live HTTP acceptance.
